# 音频转码基准（2026-10-22）

## 结论

四款工具都调用同一个 FFmpeg 二进制，MP3/AAC/M4A 的编码时间基本一致；差异主要来自 OGG 编码器选择。

- **速度/CPU 最优：OpenConverter**，总耗时 524.4s，总 CPU 554.2s；比 Sotto 原核心快约 4.5%，其中 OGG 快 18%–27%。
- **体积最小：MuXolotl**（总 1230.2 MiB），但它的 OGG 是质量档位 VBR，并非固定 320k，且许可证为 GPL-2.0/LGPL-2.1，不能直接嵌入 MIT 的 Sotto 标准版。
- **HandForge** 与 Sotto 原核心几乎同速同体积，没有明显收益。
- **标准版内嵌 OpenConverter 音频核心**（Apache-2.0）：MP3/AAC/M4A 与其它工具持平，OGG 明显更快；体积比 Sotto 原核心大约 1.9%，换取 4.5% 总耗时下降。
- 报告基于本机测试构建；标准版只内嵌 OpenConverter，不包含其它引擎代码。

## 测试条件

- 测试文件：`F:\[DSH]\RADWIMPS - 君の名は。(初回限定盤).wav`
- 大小：774,954,050 bytes；时长 01:13:12.67；44.1 kHz / 立体声 / 16-bit PCM；含一张 MJPEG 封面。
- 格式：MP3、AAC、M4A、OGG；低/中/高 = 128k / 192k / 320k。
- 每个组合顺序执行一次，记录墙钟时间、输出字节数、FFmpeg `-benchmark` 的 utime+stime，以及 CPU 时间/墙钟比。
- 统一使用 Sotto 随包 FFmpeg（N-127900）；所有引擎只保留音频（`-vn`），避免封面流影响 M4A/AAC 容器和体积。
- OGG 不是同一种编码器：OpenConverter 使用 Opus，且 320k 会钳制到 256k；MuXolotl 使用 Vorbis 质量档位 q3/q5/q7；因此 OGG 的体积不能直接按“320k”横向比较。
- HandForge 原始音频路径未加 `-vn`，遇到测试文件的封面流时 M4A 失败；OpenConverter 原始 AAC 路径也因封面映射失败。表中使用纯音频修正参数复测，保留原始失败记录在测试日志中。
